## 프로세스 / 통신 기본 개념

### stdin / stdout
프로세스(실행 중인 프로그램 하나)가 기본으로 갖는 입출력 통로.

- **stdin**(standard input) — 프로세스로 들어가는 입력 통로.
- **stdout**(standard output) — 프로세스가 내보내는 출력 통로.
- (stderr도 있음 — 에러 전용, 이 프로젝트에선 직접 안 다룸)

프로세스 두 개를 연결하면 한쪽 stdout이 다른 쪽 stdin으로 그대로
흘러들어갈 수 있음 (터미널의 `|` 파이프가 이 방식). [`MCPStdioTool`](#mcpstdiotool)이
바로 이 통로로 자식 프로세스와 대화한다.

### JSON-RPC
"무슨 형식으로 요청/응답을 주고받을지" 정한 프로토콜(약속). RPC(Remote
Procedure Call)는 "다른 프로세스에 있는 함수를 내 함수처럼 부르는" 개념이고,
JSON-RPC는 그 요청/응답을 JSON으로 표현하는 규격.

```json
// 요청
{"jsonrpc": "2.0", "method": "search-museum-objects", "params": {"query": "monet"}, "id": 1}
// 응답
{"jsonrpc": "2.0", "result": {"...": "..."}, "id": 1}
```

`id`로 어느 요청의 응답인지 짝을 맞춘다. [MCP](#mcp-model-context-protocol)가
이 형식을 쓴다.

### SSE (Server-Sent Events)
서버가 클라이언트에게 한 번 연결을 열어두고 이벤트를 계속 흘려보내는
HTTP 스트리밍 방식. [AG-UI](#ag-ui)가 이 위에서 동작해서, LLM이 답변을
토큰 단위로 생성하는 중에도 실시간으로 화면에 흘려보낼 수 있게 해준다.

## MCP (Model Context Protocol) 관련

### MCP (Model Context Protocol)
LLM 에이전트가 외부에서 만든 tool 서버를 표준 방식으로 붙여 쓸 수 있게
정한 프로토콜. "이 서버가 어떤 tool들을 제공하는지 물어보고(list), 그중
하나를 호출한다(call)"는 두 동작이 핵심이며, [JSON-RPC](#json-rpc)로
메시지를 주고받는다. 서버 실행 방식은 여러 가지가 있는데 이 프로젝트는
[stdio](#mcpstdiotool) 방식(로컬 자식 프로세스)을 쓴다.

### MCPStdioTool
`agent_framework`가 제공하는 클래스(`agent_framework/_mcp.py:2705`,
이 프로젝트에서는 `apps/agent-api/tools.py:110`에서 사용). **정체성: "자식
프로세스 하나 + 그 프로세스랑 대화하는 JSON-RPC 클라이언트 + 그걸 Agent가
이해하는 tool 인터페이스로 변환하는 어댑터", 이 셋을 한 객체 안에 다
캡슐화한 것.**

`tools.py:110` `build_metmuseum_mcp()`에서 우리가 이 객체에 넘긴 건
`command`/`args`/`allowed_tools` 같은 **설정값뿐**이다. 그 값으로
프로세스를 어떻게 띄우고, 어떻게 통신하고, 어떻게 Agent가 쓸 수 있는
tool 타입으로 바꿀지 — 그 실행 로직은 전부 이 클래스 내부
(`_mcp.py`)가 갖고 있다. 즉 우리는 "무엇을 실행할지"만 정하고, "어떻게
실행할지"는 이 객체에 위임한 것.

내부에서 하는 일 세 가지가 한 객체에 캡슐화돼 있음.

1. **자식 프로세스 관리** — `connect()` 시점에 `command`/`args`로 지정한
   프로그램(예: `npx metmuseum-mcp`)을 실제 자식 프로세스로 띄우고
   [stdin/stdout](#stdin--stdout)을 연결. `close()`로 정리.
2. **JSON-RPC 통신** — tool 호출 요청을 JSON-RPC 메시지로 만들어 stdin에
   쓰고, stdout에서 응답을 읽어 파싱.
3. **타입 변환** — 그렇게 받은 MCP tool들을 `FunctionTool`(우리가
   `@tool` 데코레이터로 만든 함수와 같은 타입)로 변환해서 Agent에게
   넘김 — 그래서 `TOOLS` 리스트(`main.py:79`)에 우리 함수랑 섞어 넣어도
   Agent가 구분 없이 다룸.

비유: 해외 지사(외부 MCP 서버)랑 전화(stdio) 연결해서 대화(JSON-RPC)하는
통역사(MCPStdioTool)를 한 명 고용해두고, 본사(Agent)는 그 통역사한테
그냥 "이거 시켜줘"라고만 하면 되는 구조.

## LLM Tool Calling 관련

### tool / `@tool` 데코레이터
Python 함수를 LLM이 호출 가능한 tool로 등록하는 `agent_framework`의
데코레이터. 함수 시그니처(타입 힌트)와 docstring을 읽어서 LLM에게 넘길
JSON 스펙(파라미터 타입, 필수 여부, 설명)을 자동 생성한다. 예:
`apps/agent-api/tools.py:120` `search_restaurants`. 스펙을 손으로 안
쓰기 때문에 함수 시그니처랑 스펙이 어긋날 일이 없음.

### function calling (tool 호출 루프)
LLM이 스스로 "이 상황엔 tool을 불러야겠다"고 판단하고, 실제 함수 실행
결과를 다시 받아서 최종 답을 만드는 반복 과정.

1. 사용자 메시지 + tool 목록을 LLM에 전달
2. LLM이 "이 tool을 이 인자로 불러줘"라고 응답 (아직 최종 답 아님)
3. 실제로 그 함수 실행
4. 실행 결과를 LLM에 다시 넣어서 재요청
5. LLM이 결과를 보고 최종 텍스트 답변 생성 (또는 2로 돌아가 다른 tool 추가 호출)

`agent_framework`의 `Agent`(`apps/agent-api/main.py:213`)가 이 루프를
내부에서 처리해서, 우리 코드엔 이 반복 로직이 안 보인다. 실제 구현은
[`FunctionInvocationLayer`](#functioninvocationlayer) 참고.

### FunctionInvocationLayer
`agent_framework/_tools.py:2836`. [function calling 루프](#function-calling-tool-호출-루프)를
실제로 도는 for문이 들어있는 클래스 — "Agent가 내부에서 알아서 돈다"고
할 때 그 "내부"가 바로 이 클래스다. `_tools.py:2926`:

```python
for attempt_idx in range(attempt_start, max_iterations):   # max_iterations 기본 10회
    response = await super_get_response(messages=prepared_messages, ...)   # ① 모델 호출
    function_processing = await _process_model_function_calls(            # ② 응답에 tool 호출 있으면 실제 실행
        response=response, ..., execute_function_calls=execute_function_calls,
    )
    if function_processing.action == "return":       # 더 부를 tool 없음 → 최종 응답
        return response
    _prepare_messages_for_next_iteration(prepared_messages, response)     # ③ 아니면 메시지에 추가하고 재반복
```

10번 반복해도 안 끝나면(무한 루프 방지 안전장치) tool 호출을 강제로 끄고
마지막 응답 한 번 더 요청하고 종료한다(`max_iterations` 초과 시 Phase 3).

우리 코드(`main.py`, `tools.py`)엔 이 반복문이 안 보이는 이유: 이 for문
자체는 라이브러리 안에 있고, 우리는 그 루프가 쓸 재료(`client`, `tools`,
`instructions`)만 `Agent(...)`에 넘긴다 — **프레임워크 = 미리 짜둔 제어
흐름(반복/분기) + 우리가 정해진 모양으로 채워 넣는 재료**라는 게 이
루프에서 그대로 드러나는 부분.

### Agent
`agent_framework.Agent` 클래스. 모델 [client](#client--provider-추상화),
tool 목록, system instructions를 하나로 묶어서 "대화 + tool 호출 루프
전체"를 처리하는 단위. `apps/agent-api/main.py:213` `local_agent`,
`:217` `foundry_agent`.

### client / provider 추상화
`OpenAIChatCompletionClient`(`apps/agent-api/main.py:50`, `:58`) — 로컬
vLLM이든 Azure Foundry든 OpenAI 호환 API를 쓰기만 하면 같은 client
클래스로 감쌀 수 있음. `Agent`는 이 client가 어느 provider인지 모르고
그냥 "메시지 보내고 응답 받는 대상"으로만 취급 — provider 차이는
`base_url`/인증 방식 설정값 차이로만 존재.

## AG-UI 관련

### AG-UI
에이전트(백엔드)와 UI(프론트)가 대화 메시지, tool 호출 상태, 공유 state
변화를 표준화된 [SSE](#sse-server-sent-events) 이벤트로 주고받기 위한
프로토콜. 백엔드는 `add_agent_framework_fastapi_endpoint`
(`apps/agent-api/main.py:214`)로, 프론트는 `HttpAgent`
(`apps/web/app/api/copilotkit/[provider]/route.ts:18`)로 각각 이 표준을
구현한 라이브러리를 쓰기 때문에, 서로 이벤트 포맷을 직접 맞춰볼 필요 없이
연결된다.

### state_update()
`agent_framework.ag_ui.state_update()`. tool이 리턴할 때 "LLM 대화용
텍스트"와 "프론트가 쓸 구조화된 데이터"를 같이 담아 보내는 함수. 예:
`apps/agent-api/tools.py:162` `state_update(text=..., state={"current_places": places})`.
`state` 쪽은 [AG-UI](#ag-ui) 스트림을 타고 프론트
[`useCoAgent`](#usecoagent)의 `state`로 그대로 반영됨 — LLM 답변 문장을
파싱해서 데이터를 뽑아낼 필요가 없어짐.

### CopilotRuntime / HttpAgent
`@copilotkit/runtime`, `@ag-ui/client`. `apps/web/app/api/copilotkit/[provider]/route.ts`.
Next.js API 라우트가 [AG-UI](#ag-ui) 프로토콜로 `agent-api`를 프론트와
연결하는 중계 지점. `agents: { default: ... }`로 등록한 이름표가
[`useCoAgent`](#usecoagent)의 `name`과 매칭된다.

### useCoAgent
`@copilotkit/react-core` 훅. `apps/web/components/MapView.tsx:22`,
`RecommendList.tsx:8`. 백엔드 [`state_update()`](#state_update)로 넘어온
공유 state를 구독해서, 값이 바뀌면 자동으로 리렌더시킨다.

### useCopilotReadable
`@copilotkit/react-core` 훅. `apps/web/components/AskAvatar.tsx:10`.
브라우저에서만 아는 정보(예: GPS 좌표)를 에이전트의 컨텍스트로 노출.
프롬프트 문자열을 직접 조립하지 않아도 LLM이 이 값을 참고하게 만든다.

### CopilotPopup
`@copilotkit/react-ui` 컴포넌트. `apps/web/components/AskAvatar.tsx:18`.
메시지 리스트/스트리밍 렌더링/로딩 상태가 내장된 완성형 채팅 UI. CSS
변수로 색상만 덮어써서 재사용한다.
